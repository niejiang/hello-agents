# CodeChatAgent 优化清单

本文记录代码分析助手后续的优化方向、建议实现方式和验收标准。参考 Codex、Claude Code 的工具调用、权限与可观察性等思路，结合当前项目规模逐步实现，不以复刻它们的完整架构为目标。

## 当前基础

- 支持命令行和本机网页（Vue 3 + Vite + FastAPI）多轮对话；会话只保存在服务进程内存中，最多保留 20 个，超出时淘汰最久未使用的会话。
- 命令行与网页共用 `services` 层：`CodeChatSession` 统一运行参数和空回答检查，`SessionStore` 负责会话存取与淘汰。
- 目录浏览、代码搜索和文件读取三个只读工具通过模型接口原生的 function calling（OpenAI 兼容的 `tools` / `tool_calls`）调用；参数按严格 JSON Schema 声明，参数无法解析时把错误返回给模型重新调用。
- 工具限定在项目目录内，排除符号链接、凭据目录和常见密钥文件（名称比较不区分大小写），并限制搜索与读取数量；单次工具结果最多 20,000 字符，回答 `max_tokens` 为 4096。
- 网页通过 SSE 逐段显示回答，工具调用以可展开卡片展示目标、行数和失败原因，支持中途停止；回答渲染 Markdown、代码高亮和“文件:行号”引用标签。
- 尚未建立搜索质量评估、会话持久化和语法级调用链分析；上下文管理已完成 M0～M2；原生工具调用和流式用量尚未用真实模型完成验证。

> 优先级含义：P0 是近期打牢基础，P1 是改善分析质量，P2 是提升持续使用体验，P3 根据实际需求决定。每个阶段完成后先验证、试用，再进入下一阶段；以下涉及的新模块名均为建议，实施时可调整。

## P0：工具执行过程与结果

### 1. 工具调用过程展示

- [ ] 显示工具名称、必要参数、执行状态和耗时。
- [x] 显示简短结果摘要；失败时显示可理解的原因。
- [ ] 对敏感参数和内容进行隐藏或脱敏。

**现状**：`backend/app/tools/code_tools.py` 中的 `CodeTool.run()` 会打印工具名和参数，还没有统一的完成状态或耗时信息。

**建议实现**：

1. 在工具执行前生成 `started` 事件，包含工具名、参数摘要及调用标识。
2. 使用 `time.perf_counter()` 在执行前后计算耗时。
3. 根据执行结果生成 `succeeded` 或 `failed` 事件；工具结果和展示文本分开处理。
4. 首先在命令行消费并打印事件；以后 Web 端可使用 SSE 或 WebSocket 消费同一类事件。
5. 先梳理 Hello-Agents 在执行工具前后的扩展点，再确定是在本项目适配器中包装，还是增加独立的执行层；不直接修改虚拟环境中的第三方源码。

**验收**：提问后能看到工具开始、结束、耗时；分别触发成功和失败，状态与实际结果一致。

**进展**：Agent 产出 `tool_start` / `tool_end` 事件（含调用标识、参数、成功与否、首行摘要、行数、是否截断）。命令行逐条打印；网页把连续的调用汇总为一行卡片（进行中显示“正在读取 …”，结束后显示“查阅了 N 处代码，M 次失败”），展开后逐条显示目标、行数和失败原因。尚未显示耗时，也未做参数脱敏（目前工具参数只有路径、行号和搜索词）。

### 2. 统一工具结果与错误

- [ ] 区分成功、失败、结果内容和提示信息。
- [ ] 区分参数错误、文件不存在、权限限制等常见情况。
- [ ] 保留工具执行状态，供模型和展示层使用。

**现状**：`CodeTool.run()` 会把部分异常转换为错误字符串；外围只判断是否抛出异常，可能误认为调用成功。

**建议实现**：

1. 在项目内部定义轻量的 `ToolResult`，包含 `success`、`data`、`message`、`error_code` 等必要字段。
2. 文件和搜索操作返回或映射到该结构；统一处理预期异常，避免把实现细节直接交给用户。
3. 在 Hello-Agents 接口边界将结果序列化为框架支持的字符串，同时将状态提供给事件展示层。
4. 统一记录未预期异常；错误信息避免暴露密钥和完整敏感内容。

**验收**：文件不存在、参数无效、读取成功分别产生可区分的结果；错误能交给模型理解，用户能看见正确状态。

### 3. 搜索结果完整性与截断提示

- [x] 告诉模型和用户结果是否可能不完整及原因。
- [ ] 分别提示匹配数量上限、扫描文件上限和跳过文件等情况。
- [x] 支持缩小范围后再次搜索；分页作为后续选项。

**现状**：搜索到 50 条或扫描超过 5000 个文件时已有文字提示，但控制台不一定显示；部分非 UTF-8、大文件或无法读取的文件会被跳过。

**建议实现**：

1. 在搜索结果中提供 `returned_count`、`truncated`、`truncation_reason` 和跳过文件数量等字段；跳过的原因可分项统计。
2. 为准确判断是否因匹配数量截断，可查找第 51 条：如果存在，则返回前 50 条并标记截断；同时保留扫描上限独立提示。
3. 将完整性状态同时传给模型和命令行展示层；提示不要把未完整扫描误认为没有结果。
4. 后续通过子目录或文件类型过滤缩小范围；有需要时再增加分页。

**验收**：分别使用少于、等于、多于 50 条匹配的样例，以及触发扫描上限的样例；展示和返回的完整性状态正确。

**进展**：结果被截断时，返回“共 N 处匹配、M 个文件，以上显示前 K 处（J 个文件）”，并按匹配数列出最多 15 个未显示的文件，提示用 path / glob 缩小范围或用 output=files 查看全部文件；扫描上限（20,000 个文件或 10 秒）和按 GB18030 解码的文件数单独说明；无结果时说明搜索范围。系统提示词要求遇到截断先缩小范围，不依据部分结果下结论。实测 openai SDK 中搜索“def create”：改动前只返回按路径排序的前 50 条，最关键的 resources/chat/completions/completions.py 被截掉且无从得知；改动后截断说明列出了该文件。尚未统计因过大、二进制而跳过的文件数（第 2 条未完成），分页暂不需要。

## P0：项目与只读边界

### 4. 项目选择与配置

- [x] 保留 `--project` 并在启动时显示实际项目目录。
- [x] 路径不存在或不是目录时明确报错。
- [ ] 考虑用本地配置或启动时输入管理默认目录。
- [x] 一个会话绑定一个项目；切换项目时创建新会话或明确重置上下文。

**建议实现**：

1. 将路径解析与校验集中到项目配置或项目服务中，输出规范化后的根目录。
2. 保留用户现有默认目录的使用习惯；如果需要跨电脑使用，将机器专属路径迁移到忽略提交的本地配置，并保留 `--project` 作为显式覆盖。
3. 在会话状态中记录项目根目录；切换时创建新 Agent / 会话，避免引用其他项目的历史代码。
4. 文档说明配置优先级、默认值和当前项目的展示方式。

**验收**：用默认路径及 `--project` 分别启动；无效路径能及时提示；切换项目后不会继续使用原项目上下文。

**调整**：“一个会话绑定一个项目”将由第 19 项取代：会话不再必须绑定项目，可在对话中按需打开多个项目。

### 19. 通用对话与按需打开项目

- [x] 打开页面即可聊天，不再要求先选择项目；一般问题直接回答。
- [ ] 对话中按语义确定用户指的是哪个项目，一个会话可同时打开多个项目（如比较两个项目）。
- [x] 以“已授权项目”清单管理可访问的项目：只有用户本人的操作能加入，可随时撤销。
- [x] 引用和工具过程标明项目，不同项目的结果不混淆。

**定位**：通用对话入口 + 只读代码分析能力（方向 A）。工具循环、事件流、上下文管理和权限分级保持与具体工具无关，以后扩展能力只需注册新工具并纳入权限分级；写文件、执行命令等能力见第 17 项。

**已授权项目（本机，跨会话、跨重启）**

1. 加入方式只有两种：用户在对话原话中写出路径；模型推断出路径时，用户在确认卡片上点“允许”。模型未经确认推断的路径不会加入。
2. 授权范围为该项目目录及其子目录，不含上级和同级目录；只读和敏感文件规则照常生效。
3. 侧栏列出全部已授权项目，可逐个移除；移除后正在使用的会话立即失去访问权限，工具返回“该项目的授权已撤销”。
4. 清单保存在本机文件中，只记录简称、路径、概况和授权时间，不保存代码内容；存放位置写入 README。
5. 不提供磁盘查找，也不配置允许的根目录（如以后需要“首次说名字即可打开”，再作为可选的整树预授权加入）。

**会话中已打开的项目（内存，单个会话）**

1. 每个会话最多同时打开 5 个，超出时移出最久未使用的项目；移出不影响授权。
2. 打开时自动生成概况（不调用模型）：简称（目录名，重名时带上级目录区分）、路径、技术栈（依据 `package.json`、`pyproject.toml`、`pom.xml`、`go.mod` 等标记文件及主要框架）、README 标题与首段、顶层目录、最近使用时间。
3. 每轮请求在本轮用户消息末尾附一段系统记录，列出已打开项目及概况、标出最近使用的项目；系统提示词和工具定义保持不变，以便命中上下文缓存。

**按语义确定项目**（写入系统提示词，由模型判断）

1. 原话中的明确路径 → 直接使用。
2. 已打开或已授权项目的简称、目录名 → 直接使用。
3. 描述性说法（“前端那个”“Java 项目”“旧版”）→ 对照技术栈、简介和路径匹配。
4. 代词（“它”“这个项目”）→ 最近使用的项目；上一轮涉及多个项目时先确认。
5. 有多个候选或无法确定 → 列出候选请用户选择，不猜测；找不到 → 请用户给出路径。

**工具**（工具集固定）

| 工具 | 参数 | 说明 |
| --- | --- | --- |
| `open_project` | `path` 或已授权项目简称 | 打开并返回概况；路径须为用户原话中的路径、已授权项目或经确认 |
| `list_files` | `project`、`path` | |
| `search_code` | `project`（可选）、`query` | 省略时搜索全部已打开项目，结果带项目名 |
| `read_file` | `project`、`path`、`start`、`end` | |

只打开一个项目时 `project` 可省略；多个项目时省略或填错，返回“请指定项目，可选：a、b”。

**权限分级**

| 情况 | 处理 |
| --- | --- |
| 用户原话中的路径 | 直接允许，并加入已授权项目 |
| 已授权项目 | 直接允许 |
| 模型推断出的其他路径 | 推送 `permission_request` 事件，界面显示确认卡片，最长等待 120 秒；拒绝、超时或停止时作为工具失败返回给模型 |
| 主目录本身、`/`、系统目录、敏感目录 | 一律拒绝 |

**引用与界面**

1. 多个项目时引用格式为 `项目名:路径:行号`（如 `my-agent:src/tools.ts:42`），单个项目时可省略项目名；前端引用标签带项目名并按项目区分颜色。
2. 历史中的工具摘要、M2 判断重复调用都包含项目名。
3. 侧栏分为“当前会话的项目”（只展示）和“已授权项目”（可移除，点击加入当前会话，不产生新授权）；顶栏显示已打开项目的简称；新增“新对话”按钮；不提供“添加项目”按钮。
4. 新增事件：`project_opened`（显示“已打开 my-agent（TypeScript）”）、`permission_request`（确认卡片）；工具卡片描述带项目名。
5. 命令行 `--project` 可多次指定以预先打开项目，也可不指定；需要确认时在终端提示 `[y/N]`。

**实施步骤**（每步单独提交）

1. 后端：会话不再必须绑定项目；已授权项目清单与概况检测；四个工具加 `project` 参数；每轮附项目清单；系统提示词中的判断规则；引用和 M2 带项目名；命令行支持。
2. 前端：打开即聊天，项目列表、项目标签、引用与工具卡片带项目名、“新对话”按钮。
3. 权限确认：`permission_request` 事件、确认接口与卡片、120 秒超时。
4. 更新 README 与本清单第 4、7、13 项。

**验收**：不打开项目可正常聊天；对话中给出路径后能读取代码；同时打开两个项目并比较，引用带正确的项目名；同名项目能区分；“它”指向最近使用的项目；未经确认的推断路径不会被打开或授权；撤销授权后无法再读取。

**进展**：第 1 步（后端）已完成。新增 `app/projects`：`profile.py` 生成项目概况（根目录及一层子目录的标记文件识别技术栈，README 标题与首段，顶层目录）；`authorized.py` 管理已授权项目清单（`data/authorized_projects.json`，读取前按修改时间重新加载，命令行与网页共用）；`project_set.py` 管理会话中已打开的项目（简称去重、最多 5 个、按最近使用移出、每次访问检查授权是否撤销、搜索全部项目时结果带简称）。用户原话中的路径按完整路径匹配（中文紧跟路径也能识别，更深的子路径或同名前缀不算），其子目录也允许；模型推断的路径在第 3 步确认流程完成前直接拒绝。工具改为 `open_project` 加带 `project` 参数的三个文件工具；项目清单附在本轮用户消息末尾；系统提示词改为通用助手并写入判断规则与引用格式；历史摘要和 M2 重复判断带项目简称；新增 `project_opened` 事件；网页创建会话时项目改为可选；命令行 `--project` 可多次指定或不指定。新增测试覆盖概况识别、路径匹配、授权与拒绝、按简称打开与重名、多项目定位、搜索全部项目、撤销授权、5 个上限、项目清单和多项目并行比较。尚待用真实模型验证按语义判断项目的效果。

第 2 步（前端）已完成：打开页面即可聊天，发送第一条消息时创建会话；侧栏分为“当前对话的项目”（简称、技术栈，多项目时标出最近使用）和“已授权项目”（点击加入当前对话、不产生新授权；撤销需二次确认）；顶栏显示项目标签；引用识别 `项目:路径:行号` 并按项目区分颜色；工具卡片描述带项目，打开项目的结果并入同一张卡片（标题如“打开项目 alpha、beta · 查阅 2 次”）；欢迎页建议问题优先使用最近授权的项目名称；新增“新对话”按钮；服务重启导致会话失效时自动开始新对话并提示重新发送。后端新增 `GET /api/projects`、`POST /api/projects/revoke`、`GET`/`POST /api/sessions/{id}/projects`。

第 3 步（权限确认）已完成：新增 `app/projects/permissions.py`（`PermissionBroker`，每个会话一个）。模型对未授权、不在用户原话中的路径调用 `open_project` 时，Agent 推送 `permission_request`（含路径和 120 秒时限）并在当前线程等待，期间响应停止请求；网页通过 `POST /api/sessions/{id}/permissions/{request_id}` 作出决定，命令行在终端提示 `[y/N]`；随后推送 `permission_resolved`（allow / deny / timeout / stopped）。允许时加入已授权项目并打开；拒绝、超时或停止时作为工具失败返回给模型，并记录本轮已拒绝的目录，同一轮内不再询问。工具执行或等待确认期间用户停止时，不再发起新的模型请求。网页显示确认卡片（路径、倒计时、拒绝 / 允许访问），处理后收为一行结果；等待时顶栏状态为“等待确认”，可按 Esc 停止。新增测试覆盖允许、拒绝后同轮不再询问、超时、等待时停止、用户原话中的路径无需确认、过期请求和确认接口。

### 5. 只读范围和敏感文件保护

- [x] 保留项目内相对路径限制和符号链接排除。
- [ ] 支持补充项目特有的排除规则。
- [x] 保持文件大小、读取行数和搜索数量限制。
- [x] 明确提示选中的代码片段可能发送至模型服务。

**建议实现**：

1. 将默认排除目录、敏感文件名及用户自定义规则统一收敛到路径策略模块；目录浏览、搜索、读取共用同一套策略。
2. 对绝对路径、`..`、符号链接和越界路径进行校验；结合实际运行环境验证边界，避免仅依靠提示词。
3. 保持只读工具范围，限制返回大小；统计因策略跳过的文件。
4. 在 README 和启动提示中说明：文件名规则不能识别所有敏感内容；云端模型会接收工具提供的相关片段。

**验收**：使用临时目录验证正常文件、项目外路径、符号链接、`.env` 和自定义排除项；三类工具对同一路径的规则一致。

## P1：提升代码查找和回答质量

### 6. 增强文本搜索能力

- [x] 支持限定子目录和文件类型。
- [x] 提供大小写与结果数量选项。
- [x] 返回搜索范围、结果数量和完整性状态。

**M0 用量观测**（基础，必须先做）

1. `.env` 新增两项配置，均为必填，缺失或无效时启动报错并提示需补充的配置项（与缺少 `LLM_MODEL_ID` 的处理一致，不使用猜测值）：
   - `LLM_MAX_INPUT_TOKENS`：模型最大输入长度，作为硬上限兜底。当前模型 `qwen4-max`（华北2 北京，非思考模式）为 991,808；其上下文长度 1,000,000，最大输出 131,072（思考模式下最大输入 983,616、最大输出 262,144）。
   - `LLM_CONTEXT_BUDGET`：实际工作预算（输入 Token），M1～M3 的阈值都按它的百分比计算。当前取 128,000。
   - 取 128,000 的原因：`qwen4-max` 北京区域不分档计价，输入 10 元、输出 30 元、缓存命中 0.5 元（显式/隐式，均为每百万 Token；显式缓存创建 5 分钟 12.5 元、1 小时 20 元）。工具循环每轮都会重发整个上下文（一个问题最多 7 次请求），128K 预算时单次请求输入最多约 1.28 元，一个问题最坏约 9 元（未计缓存）；缓存命中只按 5% 计价，保持提示词开头稳定（M3 第 4 条）的收益比之前更大。
   - 2026-11 由 `qwen3.7-plus` 切换到 `qwen4-max`：最大输入同为 991,808，两项配置数值不变。原 `qwen3.7-plus` 按输入长度分档（≤256K 输入 2 元、输出 8 元、缓存命中 0.4 元；256K～1M 为 6、24、1.2 元），当时预算留在 256K 以下以避开 3 倍单价。
   - `qwen4-max` 为混合思考模型，默认开启思考；本项目以 `enable_thinking: false` 关闭。若以后开启思考：`tool_choice` 不支持指定工具，且多轮对话须原样回传 `reasoning_content`，需相应调整工具循环。
   - 更换模型时，按百炼模型列表更新这两项。
2. 每次请求记录 `usage.prompt_tokens`、`completion_tokens`；流式请求需开启 `include_usage`，实现时验证百炼是否支持。
3. 用实测值计算“字符与 Token 的换算比例”，估算新加入内容的 Token 数。
4. 每轮结束的 `done` 事件带上本轮用量和预算占比，同时写入日志。
5. 命中缓存的输入价格只有正常价格的 20%，后续用 `usage.prompt_tokens_details.cached_tokens` 观测缓存命中情况。

验收：能看到每轮 Token 占用；估算值与下一次请求的实测值误差在 15% 以内。

**M1 硬性保护**（确定性规则，不调用模型）

1. 每轮结束只把“问题 + 回答 + 一行工具摘要”存入历史，工具摘要如“读取了 `backend/main.py:1-80`，搜索了 `create_chat_agent`”。
2. 历史超过预算 50% 时，从最早一轮开始整轮删除，不拆散工具调用与对应结果。
3. 接口返回上下文超长错误时，大幅裁剪后自动重试一次；仍失败则向用户说明原因。
4. 保留单次工具结果 20,000 字符上限。

验收：模拟 50 轮对话，请求从不超出窗口，也不出现工具调用与结果配对错误。

**M2 清理旧工具结果**（一轮之内）

1. 本轮占用超过预算 60% 时，把较早的工具结果替换为占位说明，如“[已清理：read_file backend/main.py:1-80，需要时可重新读取]”，保留最近 3 次原文；工具调用本身（名称和参数）保留。
2. 同一文件的同一行范围被重复读取时，只保留最新一次内容。
3. 工具均为只读、可重复调用，清理后需要时重新读取即可，这也满足“代码变化后重新获取证据”。

验收：一轮内连续读取 10 个大文件不超出窗口，最终回答引用的行号仍然正确。

**M3 摘要压缩**（多轮之间）

1. 历史超过预算 70% 或用户手动点击“压缩对话”时，用一次不带工具的模型调用，把较早轮次压缩为结构化摘要，最近 2～3 轮原样保留。
2. 摘要固定四部分：用户目标；已确认结论及“文件:行号”证据；已查看的文件和范围；未解决问题。摘要只作为线索，关键事实回答前重新读取文件验证。
3. 再次压缩时把“旧摘要 + 新增轮次”合并为新摘要，不每次从头总结。
4. 摘要放在系统提示之后的固定位置，保持提示词开头稳定，便于命中百炼上下文缓存；通过 `cached_tokens` 观测效果。
5. 摘要失败时退回 M1 的整轮删除；摘要只引用当前会话绑定的项目。
6. 前端收到 `context_compacted` 事件后显示“已压缩早期对话”，可展开查看摘要。

验收：压缩后追问早期结论仍能答对并给出正确行号（使用第 8 项评估样例）；不出现跨项目引用。

**M4 结构化工作记忆**

1. 每个会话维护一份“工作笔记”，记录带证据的事实（如“入口：`backend/main.py:19`”），来源包括模型通过 `note` 工具写入和从工具调用记录自动提取。
2. 笔记以精简形式常驻系统提示，不随压缩丢失；与第 10 项会话持久化一同保存，不保存密钥和完整代码片段。

验收：多次压缩后关键结论仍准确；重复读取同一文件的次数明显下降。

**M5 按需检索与子任务**（远期）

验收：同一组评估问题的平均 Token 消耗明显下降，正确率不降低。

### 13. Web 聊天界面

- [x] 显示当前项目、聊天消息和工具调用状态。
- [ ] 展示引用的文件路径、行号和代码片段。
- [ ] 后续支持创建和恢复会话。
- [x] 消息结构和组件边界预留图表内容，不要求第一版实现图表。

**建议实现**：

1. 前端拟采用 Vue 3、Vite 和 TypeScript，后端采用 FastAPI；先定义会话、消息和工具事件接口，复用现有 Agent 与工具。
2. 以本机单用户场景为第一版，先完成指定项目、发送问题、多轮对话与回答展示；不要求此阶段完成持久化或图表。
3. 逐步接入工具开始、完成、失败等事件，优先评估 SSE；当前同步 Agent 的最终回答可先一次性返回，模型逐字输出另行验证。
4. 消息采用可扩展的内容块：文本、工具事件、证据及未来图表；为未知内容类型提供安全回退，图表数据与文字、事件分开处理。
5. 项目选择方式应符合部署环境；界面说明当前模型服务和代码发送范围。会话恢复后续接入持久化服务。

**验收**：能够选择或指定允许的项目、提问、看到工具过程和证据，并完成一次追问。

**进展**：第一版已完成。页面支持输入项目路径、切换项目（释放旧会话）、多轮追问；回复渲染 Markdown、代码高亮与复制、“文件:行号”引用标签；Enter 发送，Mac 用 Option+Enter、Windows 用 Shift+Enter 换行，兼容输入法选词；窄屏下侧栏收为抽屉。第二版改用 SSE 流式接口：回答按帧合并渲染 Markdown 逐段显示；工具调用以可展开卡片展示；等待模型时显示“正在思考 / 正在整理结果”和已用秒数；发送按钮在回答中变为停止按钮（也可按 Esc），后端通过停止接口在下一段输出前结束本轮，停止超过 5 秒仍未结束时前端直接断开；未收到任何内容就出错时撤回提问并放回输入框，已输出部分内容时保留内容并标注错误；用户向上翻看时不强制滚动到底部。尚未实现被引用代码片段的展开。

### 18. 聊天中的图表展示（后续）

- [ ] 结合真实数据分析需求，在聊天消息中嵌入图表。
- [ ] 优先验证 GPT-Vis 与 Vue 的集成；需要更复杂的通用图表时评估 ECharts + Vue ECharts。
- [ ] 保留数据来源和计算依据，图表数值来自实际工具结果。

**候选技术清单**：

| 方案 | 定位与适用场景 | 后续验证重点 |
|---|---|---|
| [GPT-Vis](https://gpt-vis.antv.vision/docs) | 面向 AI 对话的图表展示；支持 Vue 集成、结构化配置及渐进渲染，适合将图表嵌入聊天消息。 | 聊天气泡内的渲染、尺寸适配、渐进更新、不完整数据和组件卸载。 |
| [ECharts](https://echarts.apache.org/en/) + [Vue ECharts](https://github.com/ecomfe/vue-echarts) | 通用图表与 Vue 组件封装；适合更复杂的统计图、交互和后续数据分析页面。 | 图表配置、响应式更新、按需引入、复杂交互与多图性能。 |

先以 GPT-Vis 为聊天图表原型；ECharts 作为通用和复杂可视化的候选。两者各有所长，是否引入以实际场景和验证结果为准，第一版聊天页面不安装图表依赖。

**建议实现**：

1. 等聊天页面可用后，选择一个具体场景，例如按文件类型统计项目文件数量；由确定性工具产生统计数据。
2. 通过结构化图表内容块传递图表类型、数据和来源；前端验证数据结构、图表类型与大小，只允许受支持的配置，不执行模型生成的代码。
3. 做 GPT-Vis 的 Vue 原型，验证聊天消息内的尺寸、自适应、卸载清理和错误回退；需要时用同一数据比较 ECharts。
4. 图表流式更新依赖后端提供对应事件；先验证完整数据渲染，再按需研究渐进更新。

**验收**：用已知数据生成图表，数值与工具结果一致，能查看来源；非法或不完整数据有明确回退，不影响聊天。图表阶段单独验证，不阻塞第一版聊天页面。

**进展**：先支持了模型输出的 Mermaid 图（流程图、时序图等），用于说明代码交互流程：引入 `mermaid@12.3.0`（按需动态加载，不增加首屏体积），回答结束或打开历史对话后渲染；`securityLevel: strict`，不执行脚本和点击跳转；把模型写出的 `&lt;` 等 HTML 转义改为 Mermaid 实体，节点文字可正常显示；图内恢复默认行高与断行，避免继承正文样式后文字被截断；语法错误时保留源码并提示，可在图与源码之间切换、复制源码；全屏查看器支持滚轮/双指缩放（以光标或手指为中心）、拖动平移、适应窗口和原始大小，宽图在消息中被缩小到原宽 70% 以下时提示点击放大。数据统计类图表（数值来自工具结果）仍按本项原计划推进。

## P3：按需求扩展

### 14. MCP 外部工具接入

- [ ] 在需要 GitHub、数据库等外部能力时评估 MCP。

**建议实现**：先选择一个只读场景，配置 MCP 客户端发现工具并调用；将外部工具并入统一的事件、超时、权限和错误处理机制。凭据在服务配置中管理，不放进提示词或日志。

**验收**：模拟或测试服务器提供一个只读工具，助手能发现、调用并处理失败；权限边界清晰。

### 15. 语义检索或向量索引

- [ ] 只在关键词搜索不足时评估索引与语义检索。

**建议实现**：从评估样例中收集关键词未召回的真实问题；以代码片段及文件位置建立可更新索引，在同一数据集对比关键词、语义和混合检索效果；设计文件变更后的更新和删除策略。

**验收**：记录召回质量、成本、索引时间及过期处理；只有效果和维护成本合适时才接入主流程。

### 16. 多 Agent 协作

- [ ] 仅当任务可以明确拆分且需要独立验证时评估。

**建议实现**：选一个可拆分的任务，例如并行分析不同模块；为子任务限定输入、工具范围和输出证据，由主流程汇总并检查冲突；与单 Agent 使用同一批问题比较效果和成本。

**验收**：结果可追溯到各子任务证据；相比单 Agent 有可衡量收益，且不会增加无法解释的遗漏。

### 17. 代码修改或执行能力

- [ ] 如未来需要，让修改代码或运行命令成为单独设计的能力。

**建议实现**：先明确操作范围、工作目录、可执行命令、沙箱和审批规则；将读取、修改和命令执行分成不同权限；修改先展示可审阅差异，执行与结果记录受控。

**验收**：授权与拒绝、越界、失败和回滚等场景都经过验证；只读模式不能产生写操作。

**扩展为通用 Agent 的方向（远期选项 B）**：在第 19 项的骨架上按风险由低到高增加能力：先联网搜索、查文档（只读）；再写文件（先展示 diff，确认后写入）；最后执行命令（沙箱与逐条审批）。每步需单独设计安全措施和评估方法，当前不实施。

## 推荐执行顺序

1. **页面聊天基础**：优先实现第 13 项中的最小聊天页面及后端接口，让用户先在页面中完成多轮聊天；消息结构为未来图表预留扩展。
2. **工具结果与过程**：按第 2 项统一成功、失败结果，结合第 1 项将工具事件逐步展示在页面；随后补充第 3 项完整性提示和第 8 项基础评估样例。
3. **项目选择与只读范围**：结合页面使用完成第 4～5 项，保持会话与项目绑定。
4. **搜索与证据**：完成第 6～7 项，用评估样例验证；再按第 9 项比较工具调用方式。
5. **会话、调用链和图表**：根据试用反馈安排第 10～12、18 项；图表使用单独原型验证，不阻塞聊天。
6. **外部工具与扩展**：出现明确需求后再选择第 14～17 项。

每阶段结束时，记录已完成内容、测试结果、已知限制及试用反馈；由使用者验证后再开始下一阶段。
